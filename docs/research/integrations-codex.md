## Integration inventory — 27 October 2026

**Best first integration:** an organizer imports approved recipients and amounts, sends each person a claim link, and the payout service sends shielded ZEC only after that person supplies a valid shielded receiver. This uses the organizer’s existing award decision and a Zcash sending wallet; a swap service, exchange, or merchant processor is unnecessary for that path. Zallet documents an Ironwood-capable `z_sendmany` RPC, though it is still described as beta, so reliable server-side sending needs an end-to-end check before any production claim. [Zallet RPC documentation](https://zcash.github.io/zallet/rpc/index.html), [Zallet status](https://zcash.github.io/zallet/)

**Reading the table:** “40h feasible” means a one-developer *demonstration* using an organizer-controlled list or the documented public surface. It does not imply partner access, authorization to move an organization’s funds, or a production integration. “UNVERIFIED” means I could not establish that detail from a current primary source. Feasibility and judge value are my assessments.

## Top five by fit × 40-hour feasibility × judge demonstration value

1. **Shielded Labs Crosslink rewards.** Its published process has repeated reward periods and a real multi-recipient ZEC allocation, so the recurring job is clear. After Shielded Labs determines each participant’s entitlement using its existing process, an operator could import `participant reference, ZEC amount, expiry`, issue one link per recipient, and let the server send Ironwood ZEC on claim; the separate viewing-key eligibility step would remain with Shielded Labs. Its older request for Orchard addresses makes confirmation of the current payout policy essential before pitching this as a live integration. [Reward allocation](https://shieldedlabs.net/crosslink-incentivized-feature-nets/), [payout process](https://shieldedlabs.net/crosslink-feature-net-reflections-on-the-first-six-weeks/)

2. **Zecathon prizes.** The organizer could turn an approved winner list into links and deliver each link through its chosen channel; the winner would provide a shielded UA on the hosted page, and an unclaimed award would never leave the treasury. That is a compact, directly relevant demonstration for the event’s judges. The public page establishes the event and prize pool, while the Telegram collection practice and actual prize-payment rules remain **UNVERIFIED** from public sources. [Zecathon](https://thezecathon.com/)

3. **ZCG, through its payout administrator.** ZCG already has approval, milestone and documentation gates. A payout link would start **after** those gates: the administrator supplies the approved amount and recipient reference, and the grantee supplies a fresh shielded address at claim time instead of leaving it in a long-lived payout record. An exported list makes the demonstration feasible without changing the grants application system; live use requires the administrator’s participation. [ZCG process](https://zcashcommunitygrants.org/selection/)

4. **ZecHub Bounties.** The precise integration point is its existing “Done, awaiting payment” state: an authorized admin could issue a claim link and record the returned transaction ID against the bounty. This has strong judge recognition, but ZecHub already registers UAs and performs batched shielded payouts, and its admin payment API is private; the gain would have to be demonstrated as temporary address collection and expiry, not as a new ability to pay shielded ZEC. [Payout workflow](https://bounties.zechub.wiki/docs/faq), [API boundary](https://bounties.zechub.wiki/docs/api)

5. **Free2Z creator awards.** A campaign or contest organizer using Free2Z could share award links with selected creators, who would claim to their own shielded UAs; the hosted page would be an organizer tool beside Free2Z’s direct-donation pages. This is technically easy to show with a manual award list and recognizable creator pages, but Free2Z already lets creators publish a payment address, and an organization-run award flow is **UNVERIFIED**. [Creator payment documentation](https://free2z.cash/docs/for-creators/)

**Novelty to show in the demo:** ZecHub already pays shielded UAs, BTCPay already has generic recipient claim links, and Vizor already exports batches of funded ZEC gift links. The specific gap to demonstrate is an **organization-controlled, treasury-held award that expires without a transfer**, with a shielded address supplied only at claim time. [ZecHub payouts](https://bounties.zechub.wiki/docs/faq), [BTCPay pull payments](https://docs.btcpayserver.org/Users/pull-payments/), [Vizor gift cards](https://github.com/chainapsis/vizor-wallet/releases)

Skipped: account-gated exchange tests, partner-admin APIs, and live ZEC transactions. The main risk is that documented wallet or RPC support has not been verified as a reliable Ironwood payout from a deployed server.
